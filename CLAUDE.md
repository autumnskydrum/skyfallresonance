@AGENTS.md

## What this is

A Next.js (App Router, TypeScript, Tailwind) blog with four feature areas: a post board (게시판), Q&A (묻고 답하기), crawled-news display (주요뉴스), and a multi-source weather comparison dashboard (날씨). The electricity bill calculator from [ElectricBillCalc](../ElectricBillCalc) is planned to be folded into this workspace later — it is not here yet.

Currently only read/list views exist for all three features; there is no auth, no write UI (posting/answering), and no real crawler implementation yet. See README.md's "구현 상태" section for the current state.

```bash
npm run dev                              # dev server (localhost:3000)
```

There is no test suite configured yet.

## Architecture

**Data layer:** `prisma/schema.prisma` defines four models — `Post`, `Question`/`Answer`, `NewsArticle`, `WeatherReading` — backed by **Neon Postgres, provisioned through Vercel's Marketplace integration** (`vercel integration add neon`, resource `neon-pink-anchor`), same DB for local dev and production — no more local SQLite file. Provisioning it this way (rather than an independent Postgres host) matters: Vercel auto-injects and keeps in sync a whole family of env vars (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `PGHOST`, etc.) scoped correctly to Production/Preview/Development, and — per the postmortem below — Vercel-provisioned resources avoid a real connectivity problem that an independently-hosted DB hit. `src/lib/prisma.ts` exports a singleton `PrismaClient`, cached on `globalThis` in dev to survive Next.js hot-reload without exhausting DB connections — always import `prisma` from there rather than instantiating a new client.

Prisma 7 requires an explicit driver adapter for SQL providers (no more implicit connection via the URL alone). This project uses `@prisma/adapter-pg` (standard Node.js Postgres driver adapter — not the edge/HTTP `@prisma/adapter-ppg` variant, since routes run on the Node runtime), wired up in `src/lib/prisma.ts`. The project moved off `@prisma/adapter-better-sqlite3` when it moved off SQLite; if the datasource provider ever changes again, swap both the adapter package and the `datasource` block in `schema.prisma` together, then **run `npx prisma generate` — the generated client bakes in the provider, so forgetting this step produces a `PrismaClientInitializationError` about adapter/provider mismatch at build time, not a schema error.** `npx prisma init` (re-run in an existing project) installs `.agents/skills/prisma-database-setup/references/` with per-provider adapter setup docs; these are gitignored local tooling, not committed.

The generated Prisma client lives at `src/generated/prisma` (per the custom `output` in `schema.prisma`) and is gitignored. Its entry point is `client.ts`, not `index.ts` — always import from `@/generated/prisma/client`, not `@/generated/prisma`. Run `npx prisma generate` after a fresh clone or any schema change.

**Routes** (`src/app/`): `/posts`, `/qna`, `/news`, `/weather` are server components that query Prisma directly and render a list or an empty-state message — no client-side data fetching. Each has `export const dynamic = "force-dynamic"` so it re-queries on every request instead of being statically prerendered at build time (the Next.js default for a page with no dynamic APIs) — without this, new posts/questions/articles wouldn't show up until the next `next build`. Keep that export on any new DB-backed page. All list pages share `src/components/page.tsx` (`PageContainer` for the outer wrapper, `EmptyState` for the "nothing yet" message, `CARD_CLASS` for the repeated card border styling — a plain class string rather than a component since call sites need different tags: `li`, `div`, `Link`) — use these for any new page rather than re-typing the wrapper markup. `src/lib/nav.ts`'s `NAV_ITEMS` is the single source of truth for the route list, consumed by both `layout.tsx`'s nav and the homepage's card grid. When adding write functionality (create post, submit question/answer), follow the same server-first pattern (Server Actions or route handlers) rather than introducing a client-side API layer, and add the route to `NAV_ITEMS`.

**News crawling:** `src/app/api/news/crawl/route.ts` is the intended entry point — a `POST` handler meant to be triggered by an external scheduler, not by users. It upserts articles into `NewsArticle` keyed on `url`. The actual fetch/parse logic belongs in `fetchLatestArticles()`, currently a stub returning `[]`. Both scheduler-triggered routes (`news/crawl` and `weather/collect`) share `src/lib/auth.ts`: `requireBearerAuth(request, envVarName)` returns a 401 `NextResponse` if the named env var is set and doesn't match the request's `Authorization: Bearer` header, or `null` to let the request through (including when the env var is unset — that's the "auth disabled" case for local dev, not a bug); `tallySettled(results)` reduces a `Promise.allSettled` array to `{ saved, failed }` counts, also shared by both routes. Add any new scheduler-triggered route the same way rather than re-inlining the check.

**Scheduling:** `.github/workflows/collect-data.yml` is the external scheduler — GitHub Actions, not Vercel Cron, because Vercel's Hobby-plan cron is capped at once/day (Pro-only for anything more frequent), which is too coarse for a "current weather" feature. The workflow calls weather collection every 30 minutes and news crawl hourly (via `github.event.schedule` matching to route to the right job — GitHub Actions doesn't support distinct schedules per job natively). It POSTs to `${{ vars.SITE_URL }}` (a repo variable, not secret — must be updated to the real deployment URL after each redeploy/domain change: `gh variable set SITE_URL --body "https://..."`) with the matching `Authorization: Bearer` header from repo secrets (`NEWS_CRAWL_SECRET` / `WEATHER_COLLECT_SECRET`, set via `gh secret set`). These repo secrets must stay in sync with the same-named Vercel env vars, or the scheduler's calls will 401.

**Weather dashboard:** `src/lib/weather/` holds the whole feature. `sources/*.ts` each export a `fetch<Source>(city): Promise<WeatherReadingResult | null>` with a uniform shape (`types.ts`) and are pure fetch-and-parse — they do NOT decide which cities they apply to. That decision lives in one place, `sources/index.ts`'s `SOURCES` registry: each entry pairs a `fetch` function with a `label` (used by `sourceLabel()`, the single source of truth for display names — don't re-list source labels elsewhere, e.g. in a page component) and an optional `isApplicable(city)` predicate. `fetchAllSources()` filters `ALL_SOURCES` by `isApplicable` *before* calling `fetch`, then runs the applicable ones concurrently via `Promise.all`, swallowing individual failures so one dead source never breaks the rest. Adding a 6th geo-gated source means adding one registry entry, not touching the fan-out logic. `cities.ts` maps ISO country code → one tracked city (`TRACKED_CITIES`, `cityForCountry()`); add countries there as needed. `geo.ts` reads the `x-vercel-ip-country` header (set automatically by Vercel's edge, absent in local dev — falls back to `"KR"`) to pick which city a visitor sees.

**All five sources are fully implemented and verified against their live APIs** (each returned a plausible real Seoul temperature during testing: Open-Meteo 30.8°C, KMA 32.0°C/맑음, WeatherAPI.com 31.2°C/Overcast, plus MET Norway and SMHI). Notes per source:

- **Open-Meteo, MET Norway**: no API key needed, applicable everywhere (no `isApplicable` entry).
- **SMHI**: `isApplicable` gated to Nordic countries (`isNordic()` in `cities.ts`) in the `sources/index.ts` registry — outside Scandinavia it has no meaningful data, so it's never even called there. It replaced its `pmp3g` API with `snow1g`/v1 on 2026-03-31 with a different response shape (`data.air_temperature` instead of a `parameters` array) — if `fetchSmhi()` starts silently returning nothing, check whether SMHI changed its API again.
- **KMA (기상청)**: `isApplicable` gated to `countryCode === "KR"` in the registry; `fetchKma()` itself only checks for `KMA_API_KEY` (`getUltraSrtNcst`, data.go.kr listing 15084084) — the country check is deliberately NOT duplicated inside the fetch function. The key must be stored as data.go.kr's raw "Encoding" value (already percent-encoded, e.g. contains literal `%2B`) and embedded in the request URL as-is — never pass it through `encodeURIComponent` or `URLSearchParams`, which would double-encode it and silently break auth. There's a second, newer data.go.kr listing (15139470, "기상청API허브 연계") that proxies to KMA's separate apihub.kma.go.kr backend with a longer forecast range, but that backend uses a structurally different (php-style, likely non-JSON) API and its own separate account system — `fetchKma()` targets the classic listing only; switching would be a rewrite, not a config change.
- **WeatherAPI.com**: needs `WEATHERAPI_KEY`, applicable everywhere; otherwise `fetchWeatherApi()` returns `null`.

Like news, collection is scheduler-driven, not per-request: `POST /api/weather/collect` processes `TRACKED_CITIES` in batches of `CONCURRENCY` (5) — `Promise.all` within a batch, sequential across batches — calling `fetchAllSources()`, `fetchAllDailySources()`, **and** `fetchAllHourlySources()` per city and upserting into `WeatherReading` (current), `WeatherDailyForecast` (this week), and `WeatherHourlyForecast` (today through this week) respectively. `WeatherReading` is unique on `[citySlug, source]` and every cycle overwrites the same row — true no-history-accumulation. `WeatherDailyForecast`/`WeatherHourlyForecast` are unique on `[citySlug, source, forecastDate]`/`[citySlug, source, forecastHour]` instead — since those dates/hours roll forward every cycle, a plain upsert alone would just accumulate old rows forever as the window moves past them, so collection also explicitly `deleteMany`s rows outside the current window for that city right before upserting (`forecastDate`/`forecastHour` before `hourlyRetentionWindow(city.timeZone).start`, and for hourly also `>= .end`). **This prune only catches genuinely past dates/hours — it does not retroactively fix a row that failed to refresh** (e.g. a transient API error or rate limit on one collection cycle leaves that row exactly as stale as it was, since the row's date hasn't become "the past" yet); it'll self-correct on the next cycle that succeeds. This was found in practice: heavy manual re-triggering of `/api/weather/collect` while developing (many rapid calls in one sitting, far more than the real 30-min cron ever produces) intermittently hit what looks like WeatherAPI.com rate-limiting, silently leaving a few future-dated `WeatherDailyForecast` rows several days stale (and in pre-`lang=ko`-fix English) until a later successful cycle overwrote them — not a bug to chase, just what "silently degrade on failure" looks like under abnormal call volume. Batching (rather than one flat `Promise.all` over all 15 cities × up to 5 sources) is deliberate: free-tier APIs like KMA and WeatherAPI.com would otherwise get ~15 simultaneous requests each cycle. `/weather` only reads from the DB. Same bearer-token gate as news crawling, via `requireBearerAuth`/`WEATHER_COLLECT_SECRET`. The current-weather card combines whatever sources returned data for that city into an average (shown large) plus a min–max range (shown as small secondary text/tooltip) — this compromise was chosen deliberately to keep the primary UI clean while not hiding source disagreement entirely; keep both when touching that UI, don't collapse it to a bare average.

**7-day forecast:** each source registry entry also carries `fetchDaily(city): Promise<DailyForecastResult[]>` (empty array, not `null`, on failure/inapplicability — consistent with the array-returning contract, unlike the single-reading `fetch`). Per-source coverage varies a lot and this is expected, not a bug: Open-Meteo/MET Norway/SMHI return up to 7+ days, WeatherAPI.com is deliberately capped at 3 (see below), and KMA's `getVilageFcst` covers only ~2-3 days by nature of the API. The weekly card (in `weather-dashboard.tsx`, see below) groups `WeatherDailyForecast` rows by date and averages whatever sources have data for that date — later days naturally have fewer contributing sources as shorter-horizon sources drop off, same ensemble philosophy as the current-weather average.

**The day-picker card is a rolling window anchored on today (오늘 + next 6 days), not a fixed calendar week.** It used to show a Mon-Sun calendar week with a `이번주 예보 (date range)` heading; that's gone — no heading at all now, just 7 day cards: `weekDateKeys()` (`aggregate.ts` — shared with the hourly forecast's `weekHours()`/`hourlyRetentionWindow()`, see below) returns today's date through today+6, always 7 keys, computed directly from today's local calendar date (no Monday lookup). `dayLabel()` (`weather-dashboard.tsx`) renders the first key as "오늘" and `weekdayShort()` for the remaining 6 — so the visible sequence is always e.g. 오늘/목/금/토/일/월/화, whatever weekday today happens to be. An earlier version of this card also included a leading "어제" card, but since `WeatherDailyForecast` only ever holds forecast data forward from today (no historical actuals are ever stored — no source in this app has a "what actually happened" endpoint), that slot was a permanent empty placeholder with nothing behind it, so it was dropped — don't re-add a "yesterday" slot without also solving the underlying no-history problem (a separate historical-log table, not covered by this feature).
- **Open-Meteo**: first-class daily-forecast endpoint (`daily=...` params) — straightforward, no aggregation needed.
- **WeatherAPI.com**: `fetchWeatherApiDaily()` requests `days=3` (`FREE_PLAN_DAYS` constant), not more, even though the free plan actually returns up to 7 days for the first while after signup (new-account trial). Request the trial-inflated number and it'll work fine right up until the trial lapses, then silently degrade — request the contractual 3 and it's correct forever. If the WeatherAPI.com plan is ever upgraded to a tier with real multi-day coverage, bump `FREE_PLAN_DAYS` deliberately rather than assuming a larger `days=` value is safe to request.
- **MET Norway, SMHI**: no daily endpoint: only hourly/6-hourly `timeseries`. `src/lib/weather/aggregate.ts`'s `aggregateDailyFromHourly()` (shared by both) groups points by UTC calendar date and computes min/max; the representative `condition` per day is taken from whichever hourly point falls closest to UTC noon. This is a deliberate simplification — grouping by UTC date rather than each city's local date can shift a day's boundary by several hours for cities far from UTC, acceptable for a rough weekly view but worth knowing if day boundaries ever look off for a specific city.
- **KMA**: needs a *second* data.go.kr API operation, `getVilageFcst` (단기예보), distinct from `getUltraSrtNcst` (초단기실황) used for current weather. This was a self-inflicted gap for a while: the original activation only registered 초단기실황조회, so `getVilageFcst` returned `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` (treated like any other failure — `[]`, degrades gracefully, no crash) from first deploy through 2026-08-12. **Fixed 2026-08-12** by adding the `getVilageFcst` operation via data.go.kr's 마이페이지 → 데이터활용 → Open API → 활용신청 현황 → (click the service name, not the public listing page's already-blocked "활용신청" button) → **"변경신청하기"** → check the additional 상세기능 checkbox → submit; auto-approved within minutes, same `KMA_API_KEY` continued to work with no code or key change. If `getVilageFcst` ever regresses to that error again, that's the exact path to re-check/re-request.

**Hourly forecast (today through +7 days):** each source registry entry also carries `fetchHourly(city): Promise<HourlyForecastResult[]>`, same empty-array-on-failure contract as `fetchDaily`. All five raw per-source fetchers funnel through `weekHours()` (`aggregate.ts`) — a shared filter/sort down to "today's local midnight → today + 7 days" (`hourlyRetentionWindow()`; `weekHours()` just calls it directly now, no separate Monday-anchored bound to keep in sync — this window's upper bound lines up with the day-picker's last visible day, today+6, giving it a full day of hourly coverage). This intentionally includes hours already past today, not just hours ahead: Open-Meteo (`timezone=UTC&past_days=1&forecast_days=9`) and WeatherAPI.com (`days=FREE_PLAN_DAYS`) both natively return full days regardless of current time, so between the two of them "earlier today" and "later this window" both get backfilled; MET Norway/SMHI's timeseries and KMA's `getVilageFcst` are forward-only from their reference time and don't need any URL change (MET Norway/SMHI's native range already reaches ~9 days; KMA's is naturally only ~2-3 days) — they simply have no contribution to hours before now, or (for KMA) to the back half of the window. No source ever provides real past-day data (there's no "what actually happened yesterday" endpoint anywhere in this stack) — yesterday has no hourly *or* daily rows, full stop; see the day-picker paragraph above. Point density still varies by source as documented previously (KMA's 3-hour steps etc.).

`/weather`'s hourly UI **and** weekly card both live in `src/app/weather/weather-dashboard.tsx` as one **client component** (`"use client"`, unlike every other page/component in this app) — `page.tsx` stays a server component that only fetches from Prisma and passes plain serializable props (dates as ISO strings) in. They share two pieces of state: `selectedDay` (always a concrete date key, defaulting to today — there's no explicit "unselected" state, so returning to today is just clicking today's own weekday card again) and `selectedHour` (a key within whichever day `selectedDay` points at, or `null`). Clicking a weekday sets `selectedDay` and resets `selectedHour` to `null`, which swaps the entire hourly strip to that day's hours (`hoursByDate`, hourly rows grouped by each hour's *local* calendar date via `localDateKey()` — not the same as `weekHours()`'s window math, which operates in absolute UTC instants) and the summary card to that day's high/low (`DailySummaryCard`). Clicking an hour within whatever day is showing drills the summary card into that specific hour instead — including for non-today days, where the summary title includes the date (`8월 13일(목) 06시 예보`) since "몇 시" alone would be ambiguous. Clicking the already-selected hour, or the hour closest to now while viewing today (`closestKey()`, computed only from *today's* hours so it can't land on a different day), clears `selectedHour` back to `null` — for today that means falling back to the real live `WeatherReading` data (deliberately preferred over the hourly "now" bucket's forecast approximation whenever both are available); for any other day it falls back to that day's `DailySummaryCard`. The hourly strip's scroll position resets on every `selectedDay` change (a `useEffect` keyed on it): scrolled to center the "지금" button when viewing today, scrolled to the start otherwise. `weatherEmoji()` maps the already-Korean-normalized `condition` string to an emoji by keyword match rather than pulling in an icon library, shared by both the hourly cards and the weekly cards. Hour labels use `Intl`'s `en-US` locale specifically — `ko-KR` already appends "시" to a bare numeric hour (e.g. `"13시"`), so formatting with `ko-KR` and then appending `+ "시"` ourselves doubles it into `"13시시"`; `en-US` gives the bare number and the component appends 시 itself. Hour labels (and all "closest/which day" comparisons) use the city's own `timeZone` (added to `CityTarget` in `cities.ts` for this reason) — the daily forecast's UTC-bucketing shortcut (see `aggregateDailyFromHourly` above) would be visibly wrong at hourly granularity, so don't reuse that shortcut here.

**A real timezone bug worth knowing if `weekDateKeys()`/`hourlyRetentionWindow()` are ever touched again:** an earlier version derived each day's date-only key by taking the real UTC instant of that day's local midnight (needed correctly for the actual fetch/prune window) and slicing its `.toISOString()` — but that instant, converted to UTC, can fall on the *previous* UTC calendar date for any positive-offset city (Seoul's local midnight is 15:00 UTC the day before), silently shifting all the labels back by one day. Fixed by keeping two separate representations: `weekDateKeys()` works entirely in plain calendar (year, month, day) arithmetic with no timezone conversion at all, while `hourlyRetentionWindow()`/`startOfLocalDay()` separately feed today's calendar numbers through `zonedMidnightToUtc()` to get the real instant needed for comparing against actual `Date` timestamps. Don't collapse these back into one code path — one needs to *not* round-trip through a real timezone conversion, the other must.

**Environment:** `DATABASE_URL`, `DIRECT_DATABASE_URL`, `KMA_API_KEY`, `WEATHERAPI_KEY`, `NEWS_CRAWL_SECRET`, `WEATHER_COLLECT_SECRET` all live in `.env` (gitignored) locally, and must be duplicated into the Vercel project's env vars for production — `.env` is never read at runtime on Vercel. `prisma.config.ts` loads `.env` via `dotenv/config` — Prisma does not auto-load `.env` on its own in this version, so don't remove that import.

**Pooled vs direct Postgres connection — read this before touching `DATABASE_URL`.** Neon (like Prisma Postgres, Supabase, etc.) gives two connection strings for the same database: a pooled one and a direct/unpooled one. They are NOT interchangeable:
- `prisma.config.ts`'s `datasource.url` (used by `prisma migrate`/`generate`/CLI) must point at **`DIRECT_DATABASE_URL`** (`DATABASE_URL_UNPOOLED` from Neon).
- `src/lib/prisma.ts`'s `PrismaPg` adapter (used by the running app) must point at **`DATABASE_URL`** (pooled).

Getting this backwards fails silently in exactly the wrong place: it works perfectly in `next dev`/`next start` locally and passes `npm run build`, only breaking once deployed. If a schema change ever needs a fresh `prisma migrate deploy` against production, do it from a local shell with `DIRECT_DATABASE_URL` set — never point Vercel's runtime `DATABASE_URL` at the direct/unpooled endpoint.

**Deployment postmortem — DB provisioning and a Vercel CLI gotcha, both worth knowing before repeating this setup:**
1. The first production deploy used an independently-provisioned Prisma Postgres DB (via `npx create-db`, unclaimed/anonymous). Every DB-backed route 500'd on Vercel (`P1001 DatabaseNotReachable`, error text "Can't reach database server at `base`") while working perfectly from this local machine — including after correctly switching to that provider's pooled endpoint. The likely cause: anonymous/unclaimed temporary databases apply anti-abuse network restrictions that block or rate-limit shared serverless-platform egress ranges (Vercel's IPs) while still allowing normal residential connections. **Fix: provision Postgres through Vercel's own Marketplace integration** (`vercel integration add neon`) instead of an independent host — it's guaranteed network-compatible with Vercel Functions by construction, and it self-injects matching env vars into the Vercel project. If a from-scratch Postgres setup ever breaks with reachability errors that only happen in production, suspect the DB host's relationship to Vercel before anything else in the app code.
2. Separately: `vercel env add <NAME> <envs>` piped a value through **PowerShell's pipeline** (`$val | vercel env add ...`) silently corrupted every secret set that way — the CLI even printed a reassuring "Removed trailing newline from stdin input," but the stored value still didn't authenticate once deployed (manifested as `/api/weather/collect` and `/api/news/crawl` both returning `{"error":"unauthorized"}` even with the exact correct `Authorization: Bearer` header). Removing and re-adding the same four secrets (`KMA_API_KEY`, `WEATHERAPI_KEY`, `NEWS_CRAWL_SECRET`, `WEATHER_COLLECT_SECRET`) via **Bash's `printf '%s' '<value>' | vercel env add ...`** instead fixed it immediately, with no other change. **Always set Vercel secret values via `printf` through Bash, never through a PowerShell pipeline** — if a Vercel-gated route mysteriously rejects a header value that looks correct, re-set it this way before debugging anything else.
3. On 2026-08-12 the project was renamed end-to-end from `autumnsky-blog` to `skyfallresonance` — local folder (`D:\skyfallresonance`), GitHub repo (`autumnskydrum/skyfallresonance`), Vercel project, and every in-repo name string (`package.json`/`package-lock.json` `name`, README title/URL, `page.tsx` h1, `layout.tsx` metadata title + nav text, and MET Norway's `USER_AGENT` string in `src/lib/weather/sources/met-norway.ts`, which embeds the GitHub URL too). One gotcha worth knowing if this ever happens again: **Vercel's default `<project-name>.vercel.app` domain is assigned once at project creation and does not follow a later project rename** — renaming the project and redeploying still auto-aliased to the *old* domain name (`autumnsky-blog.vercel.app`), not a new `skyfallresonance.vercel.app`. Getting the new name's default domain live required manually running `vercel alias set <deployment-url> skyfallresonance.vercel.app`, which then turned out to be gated by this project's `ssoProtection: all_except_custom_domains` setting (only the original creation-time default domain is exempt from deployment protection — manually added `.vercel.app` aliases are not, so they redirect to `vercel.com/sso-api` instead of serving the app). Fixed by `vercel project protection disable skyfallresonance --sso`. The old domain and its variants were later removed with `vercel alias rm <domain> --yes`. If a `.vercel.app` alias ever silently redirects instead of loading the app, suspect deployment protection before anything else.
4. Also on 2026-08-12, `/weather` was showing a temperature hours out of date (21°C displayed when it was actually ~36°C in Seoul). Cause: `.github/workflows/collect-data.yml`'s cron was `*/30 * * * *` / `0 * * * *` — both landing exactly on the hour or half-hour — and GitHub Actions documents that `schedule` triggers are delayed most right at the top of the hour under load; runs were actually landing 3-4 hours apart instead of every 30 minutes. **Fixed by offsetting both crons off the hour/half-hour mark** (`7,37 * * * *` for weather, `13 * * * *` for news) — note each job's `if: github.event.schedule == '...'` string must be updated to match the new cron literal exactly, or that job silently stops running entirely. If `/weather` (or the news crawl) ever looks stale again, check `gh run list --workflow=collect-data.yml` for actual run cadence before assuming an app-code bug.
5. Also on 2026-08-12 (while building the hourly forecast feature): the hourly strip showed wildly inconsistent temperatures across sources at the same hour (e.g. MET Norway 30.7°C vs. Open-Meteo/WeatherAPI.com ~20°C at the same "14시" bucket), only in production, never locally. Cause: Open-Meteo and WeatherAPI.com return current/hourly timestamps as offset-less "naive" strings in the *queried location's* local time (e.g. `"2026-08-12T14:00"`) — `new Date(naiveString)` interprets a string with no timezone/offset as the **runtime's own local time** per the JS spec, not the string's intended timezone. This local dev machine's OS timezone happens to be `Asia/Seoul`, so parsing coincidentally landed on the right instant for Seoul specifically; Vercel's production runtime is UTC, so every hourly reading for every non-UTC-timezone city was silently stored under the wrong `forecastHour`, shifted by exactly that city's UTC offset. **Fixed in `open-meteo.ts`/`weatherapi.ts`**: WeatherAPI.com already provides `*_epoch` fields (Unix timestamps, unambiguous) — use those instead of parsing the naive strings; Open-Meteo has no epoch field, so request `timezone=UTC` (making the naive strings actually be UTC) and append `"Z"` when parsing. **If a source's timestamp ever needs parsing again, treat any offset-less datetime string as a trap** — don't trust that local testing catches it, since this machine's timezone can silently make a broken parse look correct.

## Conventions

- All user-facing text is Korean; match the existing tone when adding UI copy.
- Tailwind only, no CSS files beyond `globals.css` — keep styling inline with utility classes as in the existing pages.
