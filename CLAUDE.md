@AGENTS.md

## What this is

A Next.js (App Router, TypeScript, Tailwind) blog with four feature areas: a post board (게시판), Q&A (묻고 답하기), crawled-news display (주요뉴스), and a multi-source weather comparison dashboard (날씨). The electricity bill calculator from [ElectricBillCalc](../ElectricBillCalc) is planned to be folded into this workspace later — it is not here yet.

Currently only read/list views exist for all three features; there is no auth, no write UI (posting/answering), and no real crawler implementation yet. See README.md's "구현 상태" section for the current state.

## Commands

```bash
npm run dev                              # dev server (localhost:3000)
npm run build                            # production build — run this after any non-trivial change to verify
npm run lint                             # ESLint
npx prisma migrate dev --name <desc>     # after editing prisma/schema.prisma
npx prisma generate                      # regenerate client only (no schema/DB change)
npx prisma studio                        # inspect dev.db contents in a GUI
```

There is no test suite configured yet.

## Architecture

**Data layer:** `prisma/schema.prisma` defines four models — `Post`, `Question`/`Answer`, `NewsArticle`, `WeatherReading` — backed by **Neon Postgres, provisioned through Vercel's Marketplace integration** (`vercel integration add neon`, resource `neon-pink-anchor`), same DB for local dev and production — no more local SQLite file. Provisioning it this way (rather than an independent Postgres host) matters: Vercel auto-injects and keeps in sync a whole family of env vars (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `PGHOST`, etc.) scoped correctly to Production/Preview/Development, and — per the postmortem below — Vercel-provisioned resources avoid a real connectivity problem that an independently-hosted DB hit. `src/lib/prisma.ts` exports a singleton `PrismaClient`, cached on `globalThis` in dev to survive Next.js hot-reload without exhausting DB connections — always import `prisma` from there rather than instantiating a new client.

Prisma 7 requires an explicit driver adapter for SQL providers (no more implicit connection via the URL alone). This project uses `@prisma/adapter-pg` (standard Node.js Postgres driver adapter — not the edge/HTTP `@prisma/adapter-ppg` variant, since routes run on the Node runtime), wired up in `src/lib/prisma.ts`. The project moved off `@prisma/adapter-better-sqlite3` when it moved off SQLite; if the datasource provider ever changes again, swap both the adapter package and the `datasource` block in `schema.prisma` together, then **run `npx prisma generate` — the generated client bakes in the provider, so forgetting this step produces a `PrismaClientInitializationError` about adapter/provider mismatch at build time, not a schema error.** `npx prisma init` (re-run in an existing project) installs `.agents/skills/prisma-database-setup/references/` with per-provider adapter setup docs; these are gitignored local tooling, not committed.

The generated Prisma client lives at `src/generated/prisma` (per the custom `output` in `schema.prisma`) and is gitignored. Its entry point is `client.ts`, not `index.ts` — always import from `@/generated/prisma/client`, not `@/generated/prisma`. Run `npx prisma generate` after a fresh clone or any schema change.

**Routes** (`src/app/`): `/posts`, `/qna`, `/news`, `/weather` are server components that query Prisma directly and render a list or an empty-state message — no client-side data fetching. Each has `export const dynamic = "force-dynamic"` so it re-queries on every request instead of being statically prerendered at build time (the Next.js default for a page with no dynamic APIs) — without this, new posts/questions/articles wouldn't show up until the next `next build`. Keep that export on any new DB-backed page. All list pages share `src/components/page.tsx` (`PageContainer` for the outer wrapper, `EmptyState` for the "nothing yet" message, `CARD_CLASS` for the repeated card border styling — a plain class string rather than a component since call sites need different tags: `li`, `div`, `Link`) — use these for any new page rather than re-typing the wrapper markup. `src/lib/nav.ts`'s `NAV_ITEMS` is the single source of truth for the route list, consumed by both `layout.tsx`'s nav and the homepage's card grid. When adding write functionality (create post, submit question/answer), follow the same server-first pattern (Server Actions or route handlers) rather than introducing a client-side API layer, and add the route to `NAV_ITEMS`.

**News crawling:** `src/app/api/news/crawl/route.ts` is the intended entry point — a `POST` handler meant to be triggered by an external scheduler, not by users. It upserts articles into `NewsArticle` keyed on `url`. The actual fetch/parse logic belongs in `fetchLatestArticles()`, currently a stub returning `[]`. Both scheduler-triggered routes (`news/crawl` and `weather/collect`) share `src/lib/auth.ts`: `requireBearerAuth(request, envVarName)` returns a 401 `NextResponse` if the named env var is set and doesn't match the request's `Authorization: Bearer` header, or `null` to let the request through (including when the env var is unset — that's the "auth disabled" case for local dev, not a bug); `tallySettled(results)` reduces a `Promise.allSettled` array to `{ saved, failed }` counts, also shared by both routes. Add any new scheduler-triggered route the same way rather than re-inlining the check.

**Scheduling:** `.github/workflows/collect-data.yml` is the external scheduler — GitHub Actions, not Vercel Cron, because Vercel's Hobby-plan cron is capped at once/day (Pro-only for anything more frequent), which is too coarse for a "current weather" feature. The workflow calls weather collection every 30 minutes and news crawl hourly (via `github.event.schedule` matching to route to the right job — GitHub Actions doesn't support distinct schedules per job natively). It POSTs to `${{ vars.SITE_URL }}` (a repo variable, not secret — must be updated to the real deployment URL after each redeploy/domain change: `gh variable set SITE_URL --body "https://..."`) with the matching `Authorization: Bearer` header from repo secrets (`NEWS_CRAWL_SECRET` / `WEATHER_COLLECT_SECRET`, set via `gh secret set`). These repo secrets must stay in sync with the same-named Vercel env vars, or the scheduler's calls will 401.

**Weather dashboard:** `src/lib/weather/` holds the whole feature. `sources/*.ts` each export a `fetch<Source>(city): Promise<WeatherReadingResult | null>` with a uniform shape (`types.ts`) and are pure fetch-and-parse — they do NOT decide which cities they apply to. That decision lives in one place, `sources/index.ts`'s `SOURCES` registry: each entry pairs a `fetch` function with a `label` (used by `sourceLabel()`, the single source of truth for display names — don't re-list source labels elsewhere, e.g. in a page component) and an optional `isApplicable(city)` predicate. `fetchAllSources()` filters `ALL_SOURCES` by `isApplicable` *before* calling `fetch`, then runs the applicable ones concurrently via `Promise.all`, swallowing individual failures so one dead source never breaks the rest. Adding a 6th geo-gated source means adding one registry entry, not touching the fan-out logic. `cities.ts` maps ISO country code → one tracked city (`TRACKED_CITIES`, `cityForCountry()`); add countries there as needed. `geo.ts` reads the `x-vercel-ip-country` header (set automatically by Vercel's edge, absent in local dev — falls back to `"KR"`) to pick which city a visitor sees.

**All five sources are fully implemented and verified against their live APIs** (each returned a plausible real Seoul temperature during testing: Open-Meteo 30.8°C, KMA 32.0°C/맑음, WeatherAPI.com 31.2°C/Overcast, plus MET Norway and SMHI). Notes per source:

- **Open-Meteo, MET Norway**: no API key needed, applicable everywhere (no `isApplicable` entry).
- **SMHI**: `isApplicable` gated to Nordic countries (`isNordic()` in `cities.ts`) in the `sources/index.ts` registry — outside Scandinavia it has no meaningful data, so it's never even called there. It replaced its `pmp3g` API with `snow1g`/v1 on 2026-03-31 with a different response shape (`data.air_temperature` instead of a `parameters` array) — if `fetchSmhi()` starts silently returning nothing, check whether SMHI changed its API again.
- **KMA (기상청)**: `isApplicable` gated to `countryCode === "KR"` in the registry; `fetchKma()` itself only checks for `KMA_API_KEY` (`getUltraSrtNcst`, data.go.kr listing 15084084) — the country check is deliberately NOT duplicated inside the fetch function. The key must be stored as data.go.kr's raw "Encoding" value (already percent-encoded, e.g. contains literal `%2B`) and embedded in the request URL as-is — never pass it through `encodeURIComponent` or `URLSearchParams`, which would double-encode it and silently break auth. There's a second, newer data.go.kr listing (15139470, "기상청API허브 연계") that proxies to KMA's separate apihub.kma.go.kr backend with a longer forecast range, but that backend uses a structurally different (php-style, likely non-JSON) API and its own separate account system — `fetchKma()` targets the classic listing only; switching would be a rewrite, not a config change.
- **WeatherAPI.com**: needs `WEATHERAPI_KEY`, applicable everywhere; otherwise `fetchWeatherApi()` returns `null`.

Like news, collection is scheduler-driven, not per-request: `POST /api/weather/collect` processes `TRACKED_CITIES` in batches of `CONCURRENCY` (5) — `Promise.all` within a batch, sequential across batches — calling `fetchAllSources()` **and** `fetchAllDailySources()` per city and upserting into `WeatherReading` (current) and `WeatherDailyForecast` (7-day) respectively. Both are unique on `[citySlug, source]` / `[citySlug, source, forecastDate]` — each collection cycle overwrites prior values rather than accumulating history. Batching (rather than one flat `Promise.all` over all 15 cities × up to 5 sources) is deliberate: free-tier APIs like KMA and WeatherAPI.com would otherwise get ~15 simultaneous requests each cycle. `/weather` only reads from the DB. Same bearer-token gate as news crawling, via `requireBearerAuth`/`WEATHER_COLLECT_SECRET`. The current-weather card combines whatever sources returned data for that city into an average (shown large) plus a min–max range (shown as small secondary text/tooltip) — this compromise was chosen deliberately to keep the primary UI clean while not hiding source disagreement entirely; keep both when touching that UI, don't collapse it to a bare average.

**7-day forecast:** each source registry entry also carries `fetchDaily(city): Promise<DailyForecastResult[]>` (empty array, not `null`, on failure/inapplicability — consistent with the array-returning contract, unlike the single-reading `fetch`). Per-source coverage varies a lot and this is expected, not a bug: Open-Meteo/MET Norway/SMHI return up to 7+ days, WeatherAPI.com's `forecast.json?days=7` genuinely returns 7 despite its own pricing page advertising only 3 for the free tier (verified live — don't "fix" this down to 3), and KMA's `getVilageFcst` covers only ~2-3 days by nature of the API. `/weather`'s `WeeklyForecast` component groups `WeatherDailyForecast` rows by date and averages whatever sources have data for that date — later days naturally have fewer contributing sources as shorter-horizon sources drop off, same ensemble philosophy as the current-weather average.
- **Open-Meteo, WeatherAPI.com**: both have first-class daily-forecast endpoints (`daily=...` params / `forecast.json`) — straightforward, no aggregation needed.
- **MET Norway, SMHI**: no daily endpoint: only hourly/6-hourly `timeseries`. `src/lib/weather/aggregate.ts`'s `aggregateDailyFromHourly()` (shared by both) groups points by UTC calendar date and computes min/max; the representative `condition` per day is taken from whichever hourly point falls closest to UTC noon. This is a deliberate simplification — grouping by UTC date rather than each city's local date can shift a day's boundary by several hours for cities far from UTC, acceptable for a rough weekly view but worth knowing if day boundaries ever look off for a specific city.
- **KMA**: needs a *second* data.go.kr API operation, `getVilageFcst` (단기예보), distinct from `getUltraSrtNcst` (초단기실황) used for current weather — **and the currently-registered `KMA_API_KEY` is only authorized for the latter.** `fetchKmaDaily()` is implemented (aggregates `TMP` items by `fcstDate` for daily min/max, per the same "don't trust TMN/TMX's sparse per-day presence" reasoning) but as of 2026-08-11 returns `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` in production, which the function treats like any other failure (returns `[]`, degrades gracefully, no crash). **To activate it: add the `getVilageFcst` operation to the existing data.go.kr 활용신청 for listing 15084084** (dev-stage additions are typically auto-approved) — no code or key change needed once that's done. This was a self-inflicted gap: the original activation guidance only mentioned registering 초단기실황조회.

**Environment:** `DATABASE_URL`, `DIRECT_DATABASE_URL`, `KMA_API_KEY`, `WEATHERAPI_KEY`, `NEWS_CRAWL_SECRET`, `WEATHER_COLLECT_SECRET` all live in `.env` (gitignored) locally, and must be duplicated into the Vercel project's env vars for production — `.env` is never read at runtime on Vercel. `prisma.config.ts` loads `.env` via `dotenv/config` — Prisma does not auto-load `.env` on its own in this version, so don't remove that import.

**Pooled vs direct Postgres connection — read this before touching `DATABASE_URL`.** Neon (like Prisma Postgres, Supabase, etc.) gives two connection strings for the same database: a pooled one and a direct/unpooled one. They are NOT interchangeable:
- `prisma.config.ts`'s `datasource.url` (used by `prisma migrate`/`generate`/CLI) must point at **`DIRECT_DATABASE_URL`** (`DATABASE_URL_UNPOOLED` from Neon).
- `src/lib/prisma.ts`'s `PrismaPg` adapter (used by the running app) must point at **`DATABASE_URL`** (pooled).

Getting this backwards fails silently in exactly the wrong place: it works perfectly in `next dev`/`next start` locally and passes `npm run build`, only breaking once deployed. If a schema change ever needs a fresh `prisma migrate deploy` against production, do it from a local shell with `DIRECT_DATABASE_URL` set — never point Vercel's runtime `DATABASE_URL` at the direct/unpooled endpoint.

**Deployment postmortem — DB provisioning and a Vercel CLI gotcha, both worth knowing before repeating this setup:**
1. The first production deploy used an independently-provisioned Prisma Postgres DB (via `npx create-db`, unclaimed/anonymous). Every DB-backed route 500'd on Vercel (`P1001 DatabaseNotReachable`, error text "Can't reach database server at `base`") while working perfectly from this local machine — including after correctly switching to that provider's pooled endpoint. The likely cause: anonymous/unclaimed temporary databases apply anti-abuse network restrictions that block or rate-limit shared serverless-platform egress ranges (Vercel's IPs) while still allowing normal residential connections. **Fix: provision Postgres through Vercel's own Marketplace integration** (`vercel integration add neon`) instead of an independent host — it's guaranteed network-compatible with Vercel Functions by construction, and it self-injects matching env vars into the Vercel project. If a from-scratch Postgres setup ever breaks with reachability errors that only happen in production, suspect the DB host's relationship to Vercel before anything else in the app code.
2. Separately: `vercel env add <NAME> <envs>` piped a value through **PowerShell's pipeline** (`$val | vercel env add ...`) silently corrupted every secret set that way — the CLI even printed a reassuring "Removed trailing newline from stdin input," but the stored value still didn't authenticate once deployed (manifested as `/api/weather/collect` and `/api/news/crawl` both returning `{"error":"unauthorized"}` even with the exact correct `Authorization: Bearer` header). Removing and re-adding the same four secrets (`KMA_API_KEY`, `WEATHERAPI_KEY`, `NEWS_CRAWL_SECRET`, `WEATHER_COLLECT_SECRET`) via **Bash's `printf '%s' '<value>' | vercel env add ...`** instead fixed it immediately, with no other change. **Always set Vercel secret values via `printf` through Bash, never through a PowerShell pipeline** — if a Vercel-gated route mysteriously rejects a header value that looks correct, re-set it this way before debugging anything else.
